# 战地一插件：多玩家查询方案

状态：第二步功能方案，尚未实现。依赖 [接口调查](bf1-api-investigation.md)。

## 目标与范围

“多用户”指在同一个插件中查询、收藏和切换多个战地一玩家账号。无需玩家登录，也不需要绑定 EA 密码。konekoroku 只是首次使用的示例输入，不自动查询、不自动收藏。

第一版支持任意 ID 查询、常用玩家收藏、最近查询、玩家切换、单玩家刷新。批量刷新、多人战绩对比和云端同步留待后续。

平台覆盖仍未确认，不提供未经验证的平台选择。数据标识中预留来源和游戏，避免未来扩展时混用。

## 用户操作规则

| 操作 | 确定行为 |
| --- | --- |
| 首次打开 | 展示搜索入口，提示可使用 konekoroku；等待用户发起查询 |
| 输入 ID 查询 | 去除首尾空格；空输入就地提示；非空值经 URL 参数编码后请求 |
| 查询成功 | 进入该玩家详情，采用 metadata.name 展示规范名称，更新最近查询 |
| 收藏 | 详情页收藏按钮保存玩家，收藏列表按添加时间倒序排列 |
| 取消收藏 | 直接移除收藏；历史和缓存保留；可以重新收藏 |
| 点击收藏或历史 | 立即切换当前玩家；先读取该玩家缓存，再按有效期决定是否请求 |
| 查看历史 | 最近成功查询最多 20 位，同一玩家重复查询置顶，不产生重复记录 |
| 删除历史 | 从最近查询移除；收藏和缓存保留 |
| 手动刷新 | 仅刷新当前玩家，跳过本地新鲜度判断；重复点击合并为同一在途请求 |
| 再次打开 | 恢复上次成功查看的玩家；如没有则进入搜索入口 |

收藏第一版最多 50 位；达到上限时提示先移除已有收藏，不静默删除。以上数量是插件本地产品选择，不是接口额度。

## 玩家标识和数据隔离

查找键：`stats2788:bf1:${trimmedName.toLowerCase()}`。

- 大小写与首尾空格不同的同名输入合并，显示名保留服务端规范形式。
- 不移除名称内部空格，不自动替换字符，不提前限定未经验证的 ID 格式。
- 成功响应中的 personaId 作为主要账号身份依据，保存为字符串；userId 同样保存为字符串。
- 已知两个名称对应相同 personaId 时合并收藏、历史和缓存引用，保留最新规范名称。
- 不凭名称相似度或曾用名列表自动合并；服务端尚未返回 personaId 时先用查找键。
- 每个账号有自己的响应、获取时间、状态和错误；不得将另一账号数据作为当前账号详情展示。

建议本地逻辑结构：

```text
schemaVersion
playersById[playerKey] = {
  source, game, personaId?, userId?, displayName, lookupNames,
  lastSuccessfulQueryAt?, favoritedAt?
}
lookupIndex[lookupKey] = playerKey
favoritePlayerIds[]
recentPlayerIds[]
lastSelectedPlayerId?
cacheByPlayerId[playerKey] = { fetchedAt, payload }
```

请求状态和进行中的请求只存在内存中，不持久化。存储损坏时允许跳过损坏项；写入应避免部分覆盖，具体采用 Scripting 可用的持久化能力实现。

## 缓存和刷新规则

- 本地新鲜期暂定 5 分钟。该时长是客户端减少重复请求的选择，不代表服务端更新周期或官方要求。
- 缓存仍在新鲜期：切换后直接展示，不自动发起请求。
- 缓存超过新鲜期：先展示该账号旧数据，标记“正在更新”，再请求新数据。
- 无缓存：显示该账号的加载状态，成功后再展示战绩。
- 手动刷新：立即请求当前账号，刷新期间旧数据可继续显示。
- 成功响应：通过结构校验后替换该账号缓存，记录客户端实际获取时间。
- 失败响应：保留该账号最后一次成功数据和获取时间，明确提示失败；不把旧数据标为已更新。
- 页面注明“获取于……”，不能将客户端获取时间称为战绩实际更新时间。
- 缓存最多保留 50 位玩家，按最近访问淘汰；收藏本身不因缓存淘汰而消失。
- 退出并重开也可恢复缓存；不存在缓存时照常请求。

## 请求调度与错误

- 一次请求一个 ID；第一版对该来源最多同时进行一个请求，避免快速切换造成请求堆积。
- 对同一玩家的在途查询去重；切换时只保留最新等待查询。
- A 请求过程中切到 B：即使 A 随后完成，也只能更新 A 缓存；当前选择仍是 B。
- 若运行环境支持取消请求，取消不再需要的请求；否则使用请求标识隔离结果。
- 请求超时暂定 20 秒；实现阶段按 Scripting 网络 API 能力核对。
- 普通网络失败不循环自动重试，用户可手动重试。
- 400：提示检查玩家 ID；404：提示未找到玩家，失败输入不加入历史或收藏。
- 已收藏玩家刷新得到 404 时保留收藏，提示该 ID 当前未找到，允许用户重新查询名称。
- 429：对来源进入共享冷却，收藏和历史切换仍可查看缓存，但不发送新请求。
- 429 有有效 Retry-After 时按服务端要求等待；否则默认冷却 60 秒。这是客户端回退规则，不是已测得的限流额度。
- 其他非成功状态或 JSON 结构异常：显示查询失败，不覆盖成功缓存。错误响应可能是纯文本，不能一律当作 JSON 解析。

## 验收场景

1. 使用 konekoroku 查询成功，规范名称显示为 KonekoRoku；收藏后可以从常用玩家进入。
2. 同一 ID 的不同大小写或首尾空格输入不会出现重复条目。
3. 查询第二位有效玩家后，两位玩家各自保有数据和获取时间，可以来回切换。
4. 快速由 A 切换至 B，A 的迟到响应不会覆盖 B 页面。
5. 同一玩家连续触发查询和刷新，仅保留一个在途请求。
6. 有效缓存不额外请求；过期缓存先展示旧数据，随后更新。
7. 网络失败仍可查看对应账号的旧数据，失败刷新不更改获取时间。
8. 空 ID、本次不存在的 ID 不写入历史；已存在收藏不会因一次失败消失。
9. 取消收藏不清除历史；删除历史不取消收藏。
10. 重开插件恢复收藏、历史、上次选择和已有缓存。
11. 模拟 429 时停止新请求，按冷却规则恢复；无需向真实接口压测。
12. 相同 personaId 的新旧名称仅保留一个玩家身份，未有身份依据的名称不自动合并。
